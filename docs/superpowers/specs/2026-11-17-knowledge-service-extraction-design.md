# 组件知识服务剥离设计

## 目标与约束

将组件知识上下文后端从统计后端完整剥离至 `/Users/natasha/data/code/component-knowledge`，沿用 Spring Boot 2.7.2、Java 8、Maven 和现有 MySQL 知识表。保留知识、草稿和版本数据，不执行建表、数据搬迁或自动发布。

## 已选方案

用户选择完整剥离，不在统计服务保留转发层；后者虽可减少前端配置变化，却会保留运行依赖。新服务建议使用 8081，统计服务保持 8080。

## 迁移边界

- 迁移各层 knowledge、modelcontext 包及知识 Mapper；复制实际依赖的通用响应、异常及 ID 工具。统计业务保留原处。
- 迁移知识 SQL、接口说明、知识文档、相关设计与计划及验证材料；混合材料只迁移知识部分，修正引用。
- 新服务具有独立 Maven 配置、运行配置、启动说明、质量脚本及架构检查配置，沿用既有技术栈。
- 前端保留接口契约及页面行为，开发代理和部署说明将 `/api/v1/knowledge`、`/api/v1/model-context` 定向至新服务，统计接口保持原目标。
- 组件知识维护技能及其 references、server.py、coverage_check.py 在新项目维护。Codex 全局技能入口改为指向项目技能目录的符号链接，MCP 启动配置直接引用项目源码，API 地址改为新服务地址。修改前保留必要的原配置备份。
- 不新增鉴权、监控、页面或无关重构，不修改现有知识正文及发布状态。

## 验收

1. 两个后端分别编译并执行适用的 Java verify 和架构检查；前端执行现有 lint、类型检查及构建。
2. 启动两个后端和前端，以真实现有数据验证知识页面、上下文、版本与草稿读取；经前端代理确认知识请求抵达新服务，统计请求仍连通原服务。
3. 执行 MCP 初始化、工具发现及真实只读知识调用，验证返回身份、版本和知识内容。技能路径解析至新项目，检查相对引用与技能覆盖校验流程；不为验证创建或发布业务草稿。
4. 核对原统计后端不再包含知识实现，文档、脚本和配置无失效路径。记录实际命令、结果及任何环境阻塞；连通性未通过不宣称完成。

## 实施顺序

先盘点依赖和运行环境，再迁移后端及配套材料，随后切换前端、技能和 MCP，最后执行静态检查与前后端、MCP、技能连通验证。
