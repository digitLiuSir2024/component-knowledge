# 组件知识维护、会话整理与版本管理设计

状态：用户已于 2026-11-17 批准，进入实施计划阶段；本文不表示已实现或获准执行建表。

评审记录：2026-11-17 初次可实施性审阅未发现问题，后续复审发现字段读取缺口、引用查询不可索引、停用口径冲突、首次迁移基线缺失及会话完整读取不足。本稿已针对五项修订；初审结论不能作为无风险证明。原设计已获批准，修订细节供用户复核。

## 1. 目标与范围

开发者在会话中主动要求整理组件知识，模型利用实际读到的前后端代码、文档和用户说明，结合数据库当前知识提出候选变更。用户在现有组件全屏详情页维护、审核并确认，确认成功后立即使用新知识版本。

支持手工维护、模型候选、语义差异、共享知识独立版本、组件完整版本清单、历史比较与恢复。范围包含组件说明、页面与流程说明、业务和技术知识、输入输出说明、适用条件、交互联动及接口契约。接口契约包含请求、响应、校验、错误码和示例。

不做自动监听会话、每轮自动整理、后台模型调用、代码恢复、独立知识管理页面、登录权限、通用操作日志、监控、导入导出。会话模型不能发布。版本记录是知识产品数据，不另建操作日志系统。

## 2. 已确认的交互与方案选择

用户选择对象独立版本加组件版本清单：变化的对象新增不可变版本；未变对象复用原版本。清单固定完整知识状态。确认后的组件版本立即供详情读取。

比较过的存储方案：

| 方案 | 取舍 |
| --- | --- |
| 全部详情快照 | 恢复直接，但每次复制全部正文 |
| 基线与变更回放 | 写入少，但完整还原和共享关系恢复复杂 |
| 对象独立版本与组件清单（选择） | 只复制变化的正文和轻量引用清单，可直接还原 |

前端方案比较：完整 meta 与数据库双向同步易冲突；全部迁数据库容易与代码定位脱节。用户接受精简代码注册信息，知识在数据库统一维护。

审核界面曾探索独立双列详情与 Markdown，对话最终选择直接复用现有 ContractPanel、子组件及 Less，在当前全屏详情页原位高亮，不重做布局和交互。

## 3. 当前项目基础

- 后端 component-context 查询已有组件说明、知识、接口、适用条件和联动；page-components 提供名称。现有查询契约见 [接口文档](../../component-knowledge-api.md)。
- 前端 component.meta.ts 同时保存身份定位和业务说明；注册表提供组件树及接口依赖。组件详情混合使用前端登记和后端知识。
- 保留 React、Vite、TypeScript、Less 和后端现有 Spring/MyBatis 技术栈，不为本功能替换依赖。

## 4. 数据权威与对象边界

### 4.1 代码登记

前端保留组件稳定 ID、源码位置、样式位置、装配结构、实际接口依赖和供数角色。能够可靠提取的结构可以生成，不能可靠识别的动态装配保留显式登记。不承诺自动分析任意调用关系。

title、summary、accepts、presents、behaviors、stateFlows 的说明性内容及联动业务描述转为数据库知识。代码事实可作为技术知识依据，不等于已确认业务意图。meta 规范版本与知识版本分开。

COMPONENT 版本明确保存 accepts（label、detail）、presents（label、note、variants）、behaviors（字符串数组）、stateFlows（label、managedBy、input、update、impact）；name/description 分别承接 title/summary。集合未登记为 null，确认无内容为空数组，不能混同。普通详情查询新增可空 componentDetails，包含这四类字段；纳管组件返回完整 componentDetails，未纳管时缺省。前端类型、解析器、状态流展示与复制上下文同任务更新：只有未纳管组件读 meta，纳管后只读 componentDetails，null 表示未登记而非回退 meta。现有其他响应字段含义保持，不再要求响应字段集合完全不变。

### 4.2 独立对象

| 对象类型 | 完整版本内容 |
| --- | --- |
| COMPONENT | 名称、说明、结构化业务输入输出等自身知识，不含代码装配真值 |
| PAGE / FLOW | 各自说明与业务上下文 |
| KNOWLEDGE | 标题、业务/技术分类、kind、正文、状态、来源 |
| INTERFACE | 接口身份、用途、请求响应字段树、校验、规则引用、错误码、示例 |
| APPLICABILITY | 知识与目标身份、适用条件、无条件标志、例外、替代知识身份 |
| PAGE_FLOW | 页面与流程关联 |
| INTERACTION | 来源组件、操作、触发条件、传递内容、自身响应 |
| COMPONENT_RELATION | 来源交互、目标组件、效果及条件 |

接口字段与示例随完整接口版本维护，不逐字段创建版本对象。对象身份沿用已有数据库主键；页面内 componentId 与数据库主键严格区分。对象版本不能修改身份字段来冒充另一个对象；身份调整作为显式新建与关联调整。

组件清单记录全部对象版本 ID，包括页面/流程、规则、关系和接口依赖。对象内部引用稳定 ID，装配历史时必须在清单中解析出对应版本，禁止隐式取最新版。对象版本正文不重复嵌套另一个共享对象正文。

关系独立版本化，两端组件可以引用同一关系版本。不同组件暂时使用不同历史关系版本时，各自详情以清单为准；展示引用版本差异，不暗中同步另一端。

### 4.3 当前与最新

对象最新已确认版本与组件当前引用版本不同。发布共享对象新版，只更新本次明确接受引用升级的组件。其他组件保留原引用，可提示存在新版。编辑共享知识时展示引用范围；首次只针对当前组件升级，避免隐式批量发布。

解除关联是修改组件清单，不物理删除知识。停用共享对象生成 EXPIRED 新版，阻止新关联和普通升级；已有历史引用仍可读取并提示停用。不得隐式改变其他组件清单。历史恢复可恢复旧引用，但必须展示已停用提示供确认。

将生命周期与内容确认分开：每个对象版本保存 lifecycle_state（ACTIVE / EXPIRED）；知识和接口内容另有 confirmation_status（PENDING / CONFIRMED）。对象头是最大已发布 version_no，停用先判断头版本的生命周期，不得过滤 EXPIRED 后回找旧 CONFIRMED 冒充当前可用对象。EXPIRE 创建内容不丢失的停用版本；已有旧引用显示原正文并附当前停用提示。检索与独立查询先排除已停用对象，再在 ACTIVE 对象中选最新 CONFIRMED 内容版本，无已确认内容则返回待确认缺口。普通 UPDATE 继承头生命周期，不得隐式重新启用；首版不提供重新启用操作。历史恢复只恢复引用，不改变对象生命周期。

## 5. 存储建议（四张新增表）

字段为逻辑设计；DDL 在实施前按当前库实际结构细化。主键使用 CUuid；表字段均带 COMMENT；结构化载荷保存 text 中的合法 JSON，不用 JSON 类型、外键、触发器或视图。

### knowledge_object_version

- id、system_code、project_code、object_type、object_id：版本及对象身份。
- version_no、previous_version_id（首次可空）：对象内递增版本与前驱。
- schema_version：载荷结构版本，旧载荷必须保持可读。
- version_purpose：NORMAL 正式内容版本 / BASELINE 迁移历史专用版本；后者不参与普通头版本和升级选择，规则见第 11 节。
- lifecycle_state、confirmation_status：生命周期与内容确认独立；非知识/接口对象的确认字段可空，不能用过滤确认状态代替生命周期检查。
- content：完整对象结构；evidence：来源定位、必要摘录及事实/要求/推断分类。
- draft_id、created_at：所属发布草稿和生成时间。
- 唯一约束：系统、项目、对象类型、对象 ID、version_no；常用读取按对象身份与版本索引。

已发布对象版本不可更新或删除。新版本必须明确从哪个版本编辑；不因候选提交就创建正式版本。

### knowledge_component_version

- id、component_id、version_no、previous_version_id（首次可空）。
- manifest：完整且有序的对象身份到版本 ID 引用，含关联关系及上下文范围。
- draft_id、summary、restored_from_version_id（非恢复可空）、created_at。
- is_current：当前发布标记。组件版本号唯一。

发布时锁定已有 knowledge_component 身份行，在同一事务内将旧版本取消当前、插入新当前版本。所有写入口使用同一锁顺序，保证一个组件只有一个当前版本；不仅依赖调用方约定。新组件的身份创建与首次发布同事务执行。

### knowledge_change_draft

- id、system_code、project_code、component_id（独立对象草稿可空）、origin（SESSION / MANUAL / RESTORE / MIGRATION）。
- revision：草稿修订号；status：DRAFT / PUBLISHED / DISCARDED。
- base_manifest_version_id：组件基准（首次基线可空）；object_bases：被编辑对象的基准版本。
- payload：候选操作、临时对象键、稳定 ID、拟改字段、关联依赖、依据与冲突。
- selected_changes：页面最终选择；published_result：发布结果版本 ID；created_at、updated_at。

草稿修订与最终确认均检查 revision。提交重试使用调用方稳定 requestId，作用域内唯一并绑定请求内容；相同请求返回原草稿，不同内容复用同键拒绝。发布锁定草稿，重复确认返回已保存结果，不重复生成版本。

已发布草稿保存此次选择和对象发布归属，从而无需额外批次表。对象独立维护可先发布无 component_id 的草稿；升级当前组件引用可以与对象发布合并在一次确认中。

### knowledge_component_reference（当前引用查询索引）

- id、system_code、project_code、component_id、component_version_id。
- object_type、object_id、object_version_id：当前组件清单中的对象引用，每个对象一行。
- 唯一键为 component_id、object_type、object_id；按系统项目、对象类型、对象 ID、component_id 建反向查询索引，版本精确匹配查询再按真实用例增加索引。

此表是清单的可重建投影，不保存知识正文或另行决定版本。发布/恢复切换当前组件版本时，同事务替换该组件全部当前引用行；历史引用仍从不可变清单读取，不为所有历史清单展开索引。共享范围、反向引用、升级提示先查索引取得候选组件，再批量读取其当前清单校验具体适用关系；禁止全量解析所有组件 text 清单。分批迁移期间，未纳管引用仍由既有关系表查询，与纳管索引结果按身份合并并标识来源；不能漏掉尚未纳管的受影响组件。旧关系不得覆盖纳管组件版本。

## 6. 会话模型整理的落地

新增一个明确触发的组件知识整理技能，以及一个 MCP 适配层。MCP 只暴露读取、提交草稿、查看结果，适配层调用现有后端应用服务，不提供发布工具。不向后端传输整个会话，不自行访问未授权资料。

1. 用户主动触发，提供或沿用明确的系统、项目、页面、组件身份。无法唯一定位时先澄清。
2. 工具返回组件当前清单版本、知识对象及稳定 ID、适用关系和可引用对象版本。
   搜索只负责定位，不作为完整知识依据；增加按 objectType、objectId、明确 versionId 读取完整内容的工具，返回条件、例外、来源、确认及生命周期、schemaVersion 和版本身份。对象历史列表与正文读取分离；正文过大按固定 versionId 分段，返回完整性标记与继续读取位置，模型读完再判断语义。首次纳管前可返回旧库内容及 sourceRevision，不能伪造正式 versionId。
3. 模型利用本会话实际读过的代码、文档与用户说明；上下文压缩后依据不可核实则标记缺口，不能宣称总结了所有资料。
4. 先匹配对象身份，再识别语义变化：措辞重写无实质变化不提交；数值、条件、范围、例外等变化列为候选。不以标题相似就确定同一知识。
5. 匹配不确定、来源冲突或推断分别列为待确认项；本次未提及不等于删除，明确的解除关联才提出移除。
6. 提交结构化草稿，返回 draftId 与前端审核地址。前端地址来自运行配置，不保存本机固定端口。
7. 用户到详情审核；模型可查询审核结果，不能代替用户确认。

候选操作包括 CREATE、UPDATE、LINK、UNLINK、UPGRADE_REFERENCE、EXPIRE。新对象先使用草稿内临时键，发布成功后由后端生成稳定 ID。禁止由模型选择版本号、写数据库或提交任意 SQL。

模型语义判断属于建议，后端验证结构、身份、类型、引用完整性及版本一致性，不声称通过确定性算法证明语义相同。

## 7. 详情页知识维护与审核

所有入口位于当前组件全屏详情，不新增管理页面。原型已获用户认可：临时原型直接导入现有 ContractPanel 及样式，业务源码未改。

- 区块提供新增知识、关联已有知识；查找范围限当前系统项目，包含独立接口与共享知识，支持明确选择版本。
- 条目提供编辑、适用条件、解除关联、版本历史；接口卡片提供契约维护。
- 编辑在页内表单或抽屉完成，保存草稿不生效；手工维护和模型候选走同一校验、对比、发布路径。
- 审核直接在原表格、卡片、段落中标记；保留目录、帮助、复制、展开折叠、来源定位和组件跳转。
- 修改显示前后内容，高亮实际变化；新增标新增；解除关联或移除保留原内容并标拟移除；未变内容保持原样。不能只靠颜色表达。
- 展示依据、共享影响、对象版本升级。接受/拒绝绑定稳定 changeId，不能绑定文本或 DOM 位置。
- 取消一项恢复该项原内容；依赖的新增规则和适用关系组成原子选择组，页面说明同步选择原因。拒绝依赖后不能留下悬空引用。
- 业务确认状态与草稿审核状态分离。接受保存不默认把 PENDING 推成 CONFIRMED；模型存在不确定性时保留待确认标记，用户可显式解决或保留。结构错误及无法定位的操作禁止发布。
- 页面顶部显示基准版本、草稿来源、选中数，底部确认发布；无实质变更不创建正式版本。
- 用户编辑草稿后，模型不能静默覆盖；修订冲突返回最新 revision 供重新读取。

正式实现使用 React 数据驱动的差异字段渲染。临时原型中的 DOM 叠加仅用于验证交互，不作为生产实现。

## 8. 发布、查询与一致性

提交携带 draftId、revision、基准组件版本及接受的 changeId。后端重新验证草稿、原子选择组、编辑对象版本和引用范围。

事务：锁定草稿、组件身份及被修改对象的既有身份行（按固定类型/ID 顺序）；核对基准；创建变化的对象版本；构成完整有效清单；发布组件版本并切换当前；替换该组件当前引用索引；标记草稿 PUBLISHED 保存结果。任一步失败全部回滚。关联/升级校验涉及的对象头也纳入固定顺序锁，避免关联确认与停用并发错过检查。

对象当前头版本以最大已发布 version_no 判断，编辑遇到新版本要求重新比较；仅引用一个已存在的历史版本不要求它是对象最新版。组件当前版本变化一律阻止旧草稿直接发布。

现有表继续负责稳定身份和必要的定位索引。版本化对象正文以版本表为权威，不把共享对象新版覆盖回旧表导致未升级组件被动改变。旧表中的历史正文在迁移后只作为迁移前数据，不再作为已纳管详情的回退来源。

component-context 的已纳管组件按当前清单装配，按第 4.1 节新增 componentDetails，其他既有字段结构与含义保持；版本/草稿管理使用单独查询能力，避免给每条现有响应强塞版本元数据。page-components 的纳管组件名称取当前组件对象版本。独立模型上下文同样补齐对应组件说明字段。独立接口查询先判断对象头是否停用，再选可用已确认内容；组件上下文仍取固定引用，不能混入当前组件未接受的新版。

知识共享组件列表、联动两端显示及反向引用按第 5 节引用索引和迁移期规则定位，不能继续仅按旧业务表判断全部引用状态。历史详情的名称、规则条件和契约都按目标清单装配；当前共享使用范围与生命周期提示明确标“当前信息”，不伪装成历史事实；代码位置作为单独当前代码登记，不属于知识恢复内容。

## 9. 历史与恢复

组件详情顶部列出版本号、摘要、时间和恢复来源。历史对象可逐版本比较；组件历史直接解析完整清单，不重放变更，不查询共享对象最新正文。

恢复目标历史清单时生成 RESTORE 草稿，以当前版本为基准，复用相同原位差异审核。一次确认后创建新的组件版本，引用所选历史对象版本；不改旧版本，不恢复代码，不更改其他组件。

恢复预览可以逐项选择；全部接受即完整恢复目标知识状态，部分接受明确标作“部分恢复自 Vn”。期间当前版本变化则重新比较。已停用或身份失效的引用展示问题，身份记录不物理删除；无法解析的版本必须报错，不能回退到最新版本。

## 10. 能力契约与错误边界

实施需要：读取组件版本上下文、按对象检索/读取历史、创建/修改/丢弃草稿、查询差异、页面发布、组件历史及恢复草稿。MCP 仅包装读取、创建候选和查询结果；页面发布不暴露给整理技能。

本稿确定能力与业务规则，不新定 URL 或替换既有接口契约。实施计划须先编写知识维护接口文档，逐项覆盖 URL、方法、字段类型、必填/可空、限制、应用错误码和请求响应示例，再实现；并同步已有查询接口文档，明确版本来源。

错误语义至少区分：对象不存在、跨项目引用、草稿修订冲突、基准已变、对象编辑冲突、非法对象结构、悬空引用、选择依赖不完整、无实质变化、草稿已丢弃、历史不可解析。沿用 HTTP200 / Result / ResponseEnum，具体数值在接口文档确定。校验失败不得部分发布。

## 11. 基线与 meta 迁移

1. 先部署版本读取、草稿审核和发布能力，尚未纳管组件继续原查询，不把旧数据伪装成正式版本。
2. 草稿分别保存 originalSnapshot（当前查询与前端实际消费合成的完整原始详情）、migrationSources（旧库与 meta 的必要原始内容、定位及摘要）及拟修改操作。基线按现有真实消费口径重现，不提前用拟修改内容覆盖；重复来源有冲突时保留两份依据，展示当前采用值及拟改值，不以来源天然优先裁决。原始快照和提案不能共用可变载荷。
3. 首次确认时重核旧库与提交 meta 的摘要；一个事务内先保存原始详情为 V1 基线，再将接受的差异保存为 V2 当前版本。没有实质修改时仅保存 V1。共享对象只在内容与基线确实相符时复用已有版本；已有最新内容不同则保留原始内容的独立历史版本，不强行用最新替代基线。版本号表示写入顺序，不代表历史内容天然适合普通升级；迁移产生的历史专用对象版本标记 version_purpose=BASELINE，普通编辑/升级及独立查询选择头内容时排除它，但历史引用可读。其生命周期继承对象当前状态，不复活已停用对象。此 purpose 字段也加入对象版本表与头版本规则；编辑头与生命周期头均只取 NORMAL 版本，首次仅有 BASELINE 时其状态作为初始化依据。首次发布结果记录 baselineVersionId 与可空的后续 componentVersionId，重复发布不得重复生成 V1/V2。
4. 纳管标志以组件存在当前清单为准。每个已纳管组件的所有显示区块统一按清单读取，不在同一区块混用旧表与新版正文。
5. 确认迁移成功后再移除该组件 meta 重复知识字段，同步类型、生成脚本、检查规则、复制上下文及前端 AGENTS/清单文档；保留组件树和接口实际依赖。

迁移前更早且没有保存的历史无法追溯恢复；首次迁移前读取的原始详情由 V1 保存，可在首次修改后恢复。不自动执行外部数据库 DDL，不自动批量删除现有资料。

## 12. 验收与实施边界

验收场景（不是新增或运行单元/E2E 测试的授权）：

- 10 条知识仅改 1 条、新增 1 条，只新增两个对象版本，其余引用保持。
- 措辞变化可被识别为无实质变更；匹配不确定显示待确认；未提及知识不被移除。
- 模型主动触发可读取基准、提交草稿并返回有效审核地址；无直接发布工具。
- 手工新增/编辑/关联与模型候选均在同一现有全屏详情审核，正常模式样式交互不变。
- 页面接受部分变更后，发布结果与审核预览一致；非法关联和不完整依赖不能发布。
- 共享知识/接口新版本不改变未确认升级组件；旧组件可独立恢复历史引用。
- 重复提交/发布不重复写；草稿和组件/对象并发冲突不覆盖。
- 历史读取不受后来共享知识修改影响；完整及部分恢复均生成新版本。
- meta 迁移后没有双重知识正文源，组件树、源码定位、名称和复制上下文仍正确。
- componentDetails 迁移后完整往返，空数组与未登记不混同；已停用对象不被旧 CONFIRMED 内容重新检出。
- 首次迁移同时修改知识后仍可恢复 V1 原始详情；共享对象已升级不污染原始基线；引用索引与当前清单同事务一致。

建议实施顺序：接口契约与存储设计 → 版本读取和基线 → 草稿、差异及事务发布 → 原详情页维护审核 → 历史恢复 → 会话技能/MCP → meta 逐组件迁移。会话接入前可手工创建草稿验证整条路径。

仅文档阶段核对内容和引用。后续代码按实际修改范围执行静态检查、编译、架构检查及前端必要检查；单元和 E2E 按项目要求另行取得授权。独立原型已构建及核对加载、目录定位，不代表完整功能验收。
